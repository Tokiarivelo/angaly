# Feature — `i18n`

**Statut : ✅ Fait.** Phase 1 — Présence digitale.

## Objet

Internationalisation FR/MG du site (spec §69 : "les traductions doivent être séparées du
code", architecture prête pour l'anglais ultérieurement). **Il n'existe pas de modèle
Prisma dédié** (pas de `Translation`) : l'i18n repose sur deux mécanismes distincts qui ne
se recouvrent pas.

1. **Contenu éditorial dynamique** (textes de sections de page gérés par le back-office) :
   porté par l'enum `Locale` (`FR`/`MG`) sur `PageSection` (`packages/database/prisma/schema.prisma`),
   une ligne par `(page, sectionKey, locale)`. Ce module `i18n` n'écrit pas dans
   `PageSection` — c'est le rôle de `content` (Phase 6) — mais définit et expose l'enum
   `Locale`/le contrat `@angaly/types` que `content` consomme, et résout la locale courante
   de la requête.
2. **Chaînes d'interface statiques** (labels de boutons, navigation, messages de formulaire)
   : catalogues JSON statiques côté frontend (`next-intl` ou équivalent), un fichier par
   locale, chargés au build/à la requête — **jamais** stockés en base ni servis par une API
   de ce module.

Ce module backend est donc volontairement mince : il ne gère que la résolution de locale
(détection, fallback) consommée par les autres modules côté serveur (`content`, et tout
module filtrant sur `Locale`), pas un CRUD de traductions.

## Emplacement Clean Architecture

`apps/api/src/i18n/`

```
domain/
  value-objects/locale.vo.ts            → valide/normalise une valeur en Locale (FR|MG), fallback FR
application/
  use-cases/
    resolve-request-locale.use-case.ts  → détermine la Locale effective (query ?locale=, cookie, Accept-Language, fallback FR)
  dtos/
    supported-locales.dto.ts
infrastructure/
  (aucune persistance — pas de repository, aucune dépendance Prisma pour ce module)
presentation/
  controllers/i18n.controller.ts        → expose la liste des locales supportées au frontend
  decorators/current-locale.decorator.ts → @CurrentLocale() réutilisable par les controllers d'autres modules
  middlewares/locale.middleware.ts      → attache la Locale résolue à la requête (req.locale)
__tests__/
  unit/resolve-request-locale.use-case.spec.ts
  integration/i18n.controller.spec.ts
```

## Modèles Prisma

Aucun modèle dédié. Ce module s'appuie sur l'enum `Locale` (`FR`, `MG`) défini dans
`packages/database/prisma/schema.prisma` et utilisé par `PageSection`
(`@@unique([page, sectionKey, locale])`) — modèle possédé et manipulé par `content`.

## Cas d'usage clés

- Résoudre la locale effective d'une requête entrante : paramètre explicite
  (`?locale=MG`) > cookie de préférence > en-tête `Accept-Language` > fallback `FR`
- Exposer la liste des locales supportées (`FR`, `MG`) au frontend (sélecteur de langue du
  footer, spec §69)
- Fournir le décorateur `@CurrentLocale()`/middleware réutilisé par `content` pour filtrer
  `PageSection` par locale sans dupliquer la logique de résolution dans chaque module

## Points d'intégration

- **`content`** (Phase 6) : consomme `Locale` et le middleware de résolution de ce module
  pour scoper `GET /api/content/sections/:page/:sectionKey` à la bonne locale ; ce module ne
  duplique jamais la logique de filtrage déjà portée par `content`.
- **Frontend (`apps/web`)** : les catalogues de chaînes statiques (next-intl ou équivalent)
  vivent entièrement côté web, hors périmètre de ce module — ce module ne sert que le
  contenu dynamique et la résolution de locale.
- **Pages consommatrices** : toutes les pages publiques (sélecteur FR/MG du footer, spec
  §69), indirectement via `content` une fois Phase 6 traitée.

## Points d'attention

Ne jamais introduire un modèle `Translation` générique tant qu'un besoin concret ne le
justifie pas explicitement dans une spec/fiche dédiée : le choix actuel (enum `Locale` +
catalogues statiques) est une simplicité délibérée, cohérente avec le périmètre FR/MG only
de la spec (l'anglais reste une extension future, pas un modèle à anticiper aujourd'hui).

## Note d'implémentation

Ce module reste effectivement "mince" comme prévu : aucun repository, aucune dépendance
Prisma. `LocaleMiddleware` est appliqué globalement (`forRoutes('*')`) dans `I18nModule` —
il attache `req.locale` à chaque requête, prêt à être consommé via `@CurrentLocale()` par
n'importe quel controller futur (notamment `content` en Phase 6) sans dépendre de l'ordre
d'import des modules. `docs/pages/navigation-mobile.md` note à raison qu'aucun endpoint
n'est *nécessaire* pour le sélecteur de langue du footer en Phase 1 (état de routing/UI côté
Next.js) — `GET /api/i18n/locales` reste utile indépendamment de ça : il évite de dupliquer
la liste `['FR', 'MG']` en dur côté frontend et pose la résolution de locale avant que
`content` (Phase 6) n'en ait besoin, conformément à l'ordre suggéré de
`docs/phases/phase-1-digital-presence.md`.
